What FAANG tests: They don't ask "name the SOLID principles." They give you a bad class design and ask you to fix it — or ask you to extend a feature and penalise you for touching code that should be closed. Know each principle as a rule you apply, not a fact you recite.
S — Single responsibility
One reason to change
Each class owns one concept. A UserService that handles auth, sends emails, and formats UI strings has three reasons to change — split it.

Interview signal: "I'd extract email sending into a NotificationService so a change in email provider doesn't touch auth logic."
O — Open/closed
Open to extension, closed to modification
Add new behaviour via new classes, not by editing existing ones. A payment processor with a switch on payment type violates OCP — add StripePayment without touching PaymentProcessor.

Pattern link: Strategy, Decorator, Template Method all enforce OCP.
L — Liskov substitution
Subtypes must be substitutable
If Square extends Rectangle and setWidth also changes height, the caller's invariant breaks — LSP violation. Classic interview trap: inheritance when composition is needed.

Test: Can you replace a parent with any child without breaking the caller?
I — Interface segregation
Don't force unused dependencies
A fat IWorker with work(), eat(), sleep() forces robots to implement eat(). Split into IWorkable, IFeedable.

Interview signal: spotting when an interface forces a class to implement methods it throws UnsupportedOperationException on.
D — Dependency inversion
Depend on abstractions
High-level modules shouldn't depend on low-level ones — both depend on interfaces. OrderService depends on IPaymentGateway, not on StripeClient directly. Enables mocking in tests.

Pattern link: Factory, DI containers, Strategy all implement DI.
OOP pillars
Encapsulation, abstraction, inheritance, polymorphism
Know the subtle distinctions: encapsulation = hide state + expose behaviour; abstraction = hide implementation details. Favour composition over inheritance — interviewers probe this constantly when you reach for extends.

Signal: "I'd use composition here — the relationship is has-a, not is-a."
What FAANG tests: You'll never be asked "name a creational pattern." You'll be asked "design a logger" and penalised if you create multiple instances. Know each pattern as a solution to a named problem.
Creational
Singleton, Factory, Abstract Factory, Builder, Prototype
1
Singleton — one instance globally. Thread-safe implementation uses double-checked locking or an enum (Java). Tested in: Logger, Config, Connection Pool. Know its testability problem: global state is hard to mock.
2
Factory / Abstract Factory — decouple object creation from usage. ShapeFactory.create("circle") returns a Shape. Abstract Factory creates families: GUIFactory returns matching Button + Scrollbar. Tested in: parsers, DB adapters, notification systems.
3
Builder — construct complex objects step by step. Avoids telescoping constructors. QueryBuilder, HttpRequest.Builder. Required when objects have many optional fields.
thread-safe singletonfactory methodtelescoping constructorimmutable builder
Structural
Adapter, Decorator, Facade, Proxy, Composite
1
Decorator — add behaviour without subclassing. BufferedReader wraps FileReader. Classic interview: design a coffee shop with condiments. Implements OCP perfectly.
2
Adapter — translate one interface to another. Legacy XML API wrapped to look like JSON API. Tested in: third-party integrations, SDK wrappers.
3
Proxy — control access. Virtual proxy (lazy load), protection proxy (auth check), remote proxy (RPC stub). Tested in: caching layer, lazy-load heavy objects.
4
Facade — simple interface over a complex subsystem. HomeTheatreFacade.watchMovie() hides 10 steps. Reduces coupling to subsystems.
wrappingopen/closedlazy loadinginterface translation
Behavioural
Observer, Strategy, Command, Iterator, Template Method, State
1
Observer — one-to-many event propagation. EventEmitter, pub/sub, UI event listeners. Tested in: notification systems, stock tickers, MVC model updates.
2
Strategy — encapsulate interchangeable algorithms. Sorter with swappable ISortStrategy. Tested in: payment processors, compression algorithms, routing.
3
Command — encapsulate a request as an object. Enables undo/redo, queueing, logging. Tested in: text editors, transaction systems, macro recording.
4
State — object changes behaviour when internal state changes. Vending machine, traffic light, order lifecycle. Replaces complex switch/if-else chains.

What FAANG tests: These 10 problems cover ~90% of what appears in actual LLD rounds at Google, Meta, Amazon, and Uber. Each one targets specific patterns. Practise designing the class diagram first, then coding the core methods.
High
LRU Cache
Core data structures: HashMap<Key, Node> + doubly-linked list. O(1) get and put. The interviewer watches how you handle the pointer manipulation on eviction and insertion — most candidates mess up the remove + addToFront sequencing.

Follow-ups: make it thread-safe (read-write lock + lock striping), distributed LRU (consistent hashing across nodes), LFU variant (min-heap or frequency buckets).

High
Parking lot
Entities: ParkingLot, Floor, Spot (Compact/Large/Handicapped), Vehicle (Car/Truck/Bike), Ticket, PaymentStrategy. Tests: inheritance hierarchy, Strategy for pricing, Singleton for the lot, Observer for spot availability.

Common mistakes: hardcoding spot types, putting pricing logic in Spot instead of a PricingStrategy, not modelling Ticket as a first-class object.

Elevator system
Entities: ElevatorController, Elevator, Request (internal/external), Direction. State machine: IDLE → MOVING_UP → MOVING_DOWN → STOPPED. Dispatch algorithm: SCAN (look algorithm) or FCFS.

Tests your state machine design and algorithm thinking. Key question: how do you handle conflicting requests efficiently? This is one of the hardest LLD problems — the scheduling logic is non-trivial.

High
Snake and ladder / Board game
Entities: Game, Board, Cell, Player, Dice, Snake, Ladder. Tests: extensibility (what if we add new cell types?), separation of game logic from I/O, Strategy for dice behaviour.

Key design question: should Snake and Ladder share a parent? Yes — both are Jump objects with a start and end. This is the insight interviewers look for.

Logger / rate limiter
Logger: Singleton + Chain of Responsibility. Log levels (DEBUG/INFO/WARN/ERROR), multiple appenders (file, console, remote), configurable formatters. Decorator for adding timestamp/correlation ID.

Rate limiter: Strategy for algorithms (token bucket, leaky bucket, fixed window, sliding window). Thread-safe counter with atomic operations. Follow-up: distributed rate limiter with Redis.

High
Vending machine
Classic State pattern problem. States: IDLE → HAS_MONEY → ITEM_SELECTED → DISPENSING → CHANGE_RETURN. Each state handles events (insertCoin, selectItem, cancel) differently.

Also tests: inventory management, payment handling, error states (out of stock, insufficient funds). Key: transitions should be encoded in the State objects, not in a monolithic switch statement.

Hotel: Room types, Booking, Guest, Invoice, availability calendar. Key: model time-based availability correctly — overlapping booking detection is the core algorithm.

Medium
File system / in-memory filesystem
Composite pattern: FileSystemEntry is either a File or Directory. Directory holds a list of FileSystemEntry. Operations (size, search, delete) recurse uniformly. Iterator for traversal.

Follow-ups: permissions system (Decorator or separate ACL), versioning (Memento pattern), search by content (Visitor pattern). Tests whether you can model recursive structures cleanly.

Pub/sub message broker (simplified)

Follow-ups: at-least-once vs at-most-once delivery, offset tracking (Kafka model), fan-out vs direct routing. This bridges LLD and system design — the interviewer can pivot either direction.

The 5-step LLD interview framework used at Google, Meta, and Amazon: most candidates jump to coding within 2 minutes. This is wrong. The interviewer is watching how you think, not just what you produce.
Step 1 — Clarify (3 min)
Scope before designing
Ask: what actors use this? What are the core use cases? What do we NOT need to handle? What scale — in-memory or persistent? Single-process or distributed?

Never assume. "Design a parking lot" could mean a kiosk, a backend service, or a full system. Nail the scope or you'll design the wrong thing.
Step 2 — Use cases (3 min)
List the behaviours, not the classes
Write 5–7 use cases as sentences: "A driver parks a vehicle and gets a ticket." "A cashier processes payment." "A manager views occupancy."

Classes emerge from use cases, not the other way around. Interviewers penalise candidates who jump to ParkingLot.java before understanding what it needs to do.
Step 3 — Core entities (5 min)
Noun extraction + relationships
Extract nouns from your use cases — those are your candidate classes. Draw rough associations: one-to-many, has-a, is-a. Explicitly state composition vs inheritance decisions.

"Vehicle is abstract — Car, Truck, Bike extend it. Spot has-a SpotType enum rather than a subclass per type — I'd only subclass if behaviour differs."
Step 4 — Identify patterns (3 min)
Name the patterns before coding
Before writing code, say: "I'll use Strategy for pricing so adding a new tier doesn't touch Spot. I'll use Singleton for ParkingLot since there's one instance. I'll use Observer to notify a display when a spot changes state."

This is the highest signal moment of the interview — it shows you design with intent.
Step 5 — Code the core (20 min)
Interfaces first, then key methods
Define interfaces before concrete classes. Code the 2–3 methods the interviewer cares most about (usually: the main operation + one complex edge case). Leave helpers as stubs with comments.

"I'll implement park() and unpark() fully, and stub out calculateFee() — want me to implement that next?"
Anti-patterns to avoid
What tanks candidates
Anemic models (classes with no behaviour — just getters/setters). God classes (one class doing everything). Inheritance where composition fits. Hardcoded enums that block extension. Missing interfaces — depending on concretions. Not narrating your decisions — silent coding tells the interviewer nothing.
6-week LLD study plan — parallel with your DSA prep. 3–4 sessions per week, 90 minutes each.
Week 1–2
SOLID + design patterns foundation
1
Read each SOLID principle with a bad code example and a fixed version. Don't memorise definitions — memorise the violation and the fix.
2
Implement from scratch: Singleton (thread-safe), Factory, Builder, Observer, Strategy, Decorator, Command. In your primary language, without looking at references.
3
For each pattern: write one sentence describing the problem it solves, one real-world example, and one FAANG problem it appears in.
Week 3–4
Core LLD problems — design then code
1
Solve in order: LRU Cache → Parking Lot → Vending Machine → Snake & Ladder → Logger. Each session: 15 min design (no code), 45 min coding, 15 min review against a reference.
2
After each: write down which patterns you used and why. If your design differs from a reference, understand why — both can be valid.
3
Add thread safety to LRU Cache and Logger — these are the two most common follow-ups at FAANG.
Week 5–6
Advanced problems + mock interviews
1
Elevator system, Chess, File system, Pub/Sub. These require multi-pattern thinking — expect to combine State + Observer + Command in a single design.
2
Run 3 timed mock sessions (45 min each) narrating aloud. Record yourself if possible — review the narration, not just the code.
3
Review your weakest problem twice more. The goal: any of the 10 classic problems should take under 30 min from blank page to working core code.
