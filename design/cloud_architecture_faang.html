What FAANG tests: Not which cloud provider you prefer — but whether you can reason about the tradeoffs between compute models under different traffic patterns, latency constraints, and operational costs.
High
Containers & Kubernetes
1
Container model: image layers, copy-on-write filesystem, namespaces + cgroups for isolation. Know why containers are not VMs — shared kernel, faster startup, no hypervisor overhead.
2
K8s core objects: Pod, Deployment, Service, ConfigMap, Secret, HPA, PVC. Know the difference between a Deployment (stateless) and a StatefulSet (ordered, stable network identity — for databases, Kafka).
3
Scheduling & rolling updates: how the scheduler places pods (node affinity, taints/tolerations, resource requests vs limits). Rolling update strategy — max unavailable, max surge. How readiness probes gate traffic during rollout.
4
Service mesh (Istio/Linkerd): sidecar proxy model, mTLS between services, traffic shaping (canary weights), observability (distributed tracing without code changes).

High
Serverless — functions & containers
1
Cold start problem: function container must be initialised on first invocation — adds 100ms–2s latency. Mitigations: provisioned concurrency (keep containers warm), smaller runtimes (Node/Python over Java), minifying dependencies.
2
When to use serverless: event-driven, unpredictable traffic, short-lived tasks (image resize, webhook handler, ETL trigger). When NOT to: long-running jobs (>15 min), persistent connections (WebSockets), latency-sensitive hot paths.
3
Concurrency model: each invocation is isolated — no shared memory between calls. State must live in external stores (DynamoDB, Redis). At-most-once vs at-least-once execution guarantees.

Medium
Autoscaling — reactive & predictive
1
HPA (Horizontal Pod Autoscaler): scales pod count based on CPU/memory or custom metrics (queue depth via KEDA). Lag between metric crossing threshold and pods being ready — design for this gap with circuit breakers.
2
Scale-in risk: aggressively scaling down drops in-flight requests. Use connection draining, PodDisruptionBudgets, and termination grace periods. Scale-out is safe; scale-in needs care.
3
Predictive scaling: scheduled scaling for known traffic patterns (lunch rush, market open). ML-based predictive scaling (AWS) for recurring patterns. Reduces cold-start lag at known peaks.

What FAANG tests: Given a system design, interviewers ask "what happens when X fails?" You need to enumerate failure modes and recovery strategies — not just claim "it's highly available."
High
Multi-region HA architecture
1
Active-active vs active-passive: active-active serves traffic from multiple regions simultaneously — zero failover time but requires conflict-free data replication. Active-passive has a warm standby — failover takes seconds to minutes, but simpler consistency.
2
Data replication lag: cross-region replication is async — lag can be 100ms–seconds. During failover, reads may return stale data. Design decisions: can your use case tolerate stale reads? If not, synchronous replication (high write latency) or route reads to primary always.
3
Failover mechanics: DNS-based (Route53 health checks, TTL matters), anycast routing, global load balancer. RTO (recovery time objective) vs RPO (recovery point objective) — interviewers ask you to quantify these.
4
Cell-based architecture: FAANG-specific pattern — partition users into cells (each cell is an independent stack). A failure in cell 3 doesn't affect cells 1, 2. Blast radius containment. Amazon uses this for Route53 and DynamoDB.
active-activeRTO / RPOreplication lagcell architectureanycast
High
Resilience patterns — circuit breaker, bulkhead, retry
1
Circuit breaker: three states — CLOSED (normal), OPEN (failing fast without calling downstream), HALF-OPEN (probe with limited traffic). Prevents cascading failures when a dependency is degraded. Hystrix/Resilience4j implement this.
2
Retry with exponential backoff + jitter: naive retries amplify load on a struggling service. Jitter randomises retry timing across clients, preventing thundering herd. Know the formula: min(cap, base * 2^attempt) + random(0, jitter).
3
Bulkhead: isolate resource pools per dependency — separate thread pools for payment service, inventory service. A slow payment call doesn't exhaust threads serving inventory. Titanic metaphor: watertight compartments.
4
Timeout + deadline propagation: always set timeouts. Propagate deadlines across service calls — if the user's request has 200ms left, don't call a service with a 500ms timeout. gRPC and HTTP context cancellation enable this.

High
Deployment strategies — canary, blue-green, feature flags
1
Blue-green: two identical environments — switch traffic atomically. Instant rollback (flip DNS/LB back). Cost: double infrastructure during transition. Good for: high-risk releases, database schema changes.
2
Canary: route 1–5% of traffic to new version, observe error rates + latency, graduate to 100% if healthy. Slower than blue-green but cheaper and gives real-signal validation. Used by Netflix, Google.
3
Feature flags: decouple deploy from release. Code ships dark, flag enables it for % of users or specific cohorts. Enables A/B testing, kill switches, gradual rollout independent of deployment cadence.

Chaos engineering & game days
1
Principles: form a hypothesis ("the system will serve <200ms p99 if one AZ is lost"), define blast radius, run in production with limited scope, measure against SLOs. Netflix's Chaos Monkey kills random instances.
2
Fault injection types: latency injection (add 500ms to downstream calls), error injection (return 503 from dependency), resource exhaustion (fill disk, OOM), network partition (drop packets between services).

What FAANG tests: Cloud networking appears in every system design round — as the glue between components. Know how traffic flows from user to service and back, and what can fail at each hop.
High
Load balancers — L4 vs L7, global vs regional
1
L4 (TCP/UDP): routes by IP + port, no application awareness. Faster, lower overhead. Cannot do path-based routing, header inspection, or TLS termination based on hostname. Used for raw throughput (gaming, streaming).
2
L7 (HTTP/gRPC): routes by URL path, headers, cookies. Enables: path routing (/api → service A, /static → CDN), A/B traffic splitting, sticky sessions, WAF integration, TLS termination. Cost: higher CPU per connection.
3
Global load balancer (Anycast): single IP resolves to nearest PoP. Routes to healthiest origin. Used for latency-sensitive global services. AWS Global Accelerator, GCP Premium Tier.
L4 vs L7path routingTLS terminationanycaststicky sessions
High
VPC, subnets, security groups, peering
1
VPC fundamentals: private isolated network. Public subnets (route to internet gateway) vs private subnets (no direct internet — use NAT gateway for egress, VPC endpoints for AWS service access without traversing internet).
2
Security groups vs NACLs: security groups are stateful (return traffic automatic), instance-level. NACLs are stateless (must allow both directions), subnet-level. Use security groups for service-to-service; NACLs for broad subnet policies.
3
VPC peering vs Transit Gateway: peering is non-transitive (A↔B, B↔C does not give A↔C). Transit Gateway is a hub — connect hundreds of VPCs centrally. Use peering for simple two-VPC connections; Transit Gateway for mesh or hub-spoke topologies.
public vs private subnetNAT gatewayVPC endpointsecurity groupTransit Gateway
Medium
CDN architecture & edge compute
1
Cache hierarchy: PoP (point of presence) → regional edge → origin shield → origin. Cache-hit serves from PoP in <10ms. Shield aggregates misses so origin sees one request per unique URL, not one per PoP.
2
Cache invalidation: TTL-based (simple but stale window), event-based purge (instant but complex). Surrogate keys allow purging all assets tagged with product-123 in one API call.
3
Edge compute (Cloudflare Workers, Lambda@Edge): run code at PoP — A/B testing, auth token validation, geo-routing, response personalisation — without round-tripping to origin. Sub-5ms overhead.
origin shieldcache invalidationsurrogate keysedge computegeo-routing
Medium
API gateway & service mesh
1
API gateway responsibilities: authn/authz at edge, rate limiting, request routing, protocol translation (REST↔gRPC), response caching, schema validation, usage metering. Do not put business logic here.
2
Service mesh (east-west traffic): handles service-to-service (internal) traffic. API gateway handles north-south (external). Sidecar proxy (Envoy) intercepts all traffic — mTLS, tracing, retries, circuit breaking without app code changes.

What FAANG tests: Storage selection is a core system design skill. Interviewers watch whether you default to "use Postgres" for everything or match the access pattern to the right store.
Object storage
S3 / GCS / Blob Storage
Immutable, infinitely scalable, cheap. For: images, video, backups, ML training data, static assets, data lake raw layer. Key design: pre-signed URLs for secure client-direct upload (avoids proxying large files through your servers). Lifecycle rules for tiering to cold storage.

Interview use: any design that handles user media uploads.
Managed databases
RDS, Aurora, Spanner, Firestore
RDS Multi-AZ = synchronous standby (automatic failover ~30s). Aurora = shared storage volume, up to 15 read replicas, faster failover. Spanner = globally distributed, externally consistent, SQL — used when you need strong consistency across regions.

Interview use: explain why you'd pick Aurora over RDS, or Spanner over Aurora.
Managed queues & streams
SQS, Kinesis, Pub/Sub, EventBridge
SQS: at-least-once, no ordering (FIFO queue for ordering). Kinesis/Kafka: ordered within partition, replay, consumer groups. EventBridge: event routing with schema registry — good for loosely coupled microservice events.

Interview use: every async design needs a queue — explain which and why.
Caching layer
ElastiCache Redis vs Memcached
Redis: rich data types (sorted sets for leaderboards, streams, geospatial), persistence, pub/sub, Lua scripting. Memcached: pure key-value, multi-threaded, simpler. Choose Redis for almost everything — only pick Memcached when you need horizontal scaling without persistence and simpler ops.

Know: Redis Cluster vs Sentinel failover model.
Data warehouse & lake
Redshift, BigQuery, Snowflake, S3 + Athena
Columnar storage, MPP (massively parallel processing), separation of storage and compute. S3 + Athena = serverless query over data lake — pay per query, no cluster. BigQuery = fully managed, serverless, automatic scaling.

Interview use: analytics layer in any large-scale system design.
Storage selection guide
Match pattern to store
Structured + ACID → RDBMS. High write throughput + simple lookup → DynamoDB/Cassandra. Full-text search → Elasticsearch. Time-series → TimescaleDB / InfluxDB. Graph traversal → Neptune / Neo4j. Files / blobs → S3. Session / cache → Redis. Leaderboard → Redis sorted set.
What FAANG tests: You're expected to know IaC at the conceptual level — why it exists, what problems it solves, and how CI/CD pipelines gate deployments. Certification-level detail is not expected.
High
Infrastructure as Code — Terraform & CDK
1
Why IaC: reproducible environments, version-controlled infrastructure, drift detection, peer-reviewed changes. The alternative — clicking in console — produces snowflake servers and undocumented config.
2
Terraform model: declarative — describe desired state, Terraform plans the diff, applies atomically. State file tracks real-world mapping. Remote state (S3 + DynamoDB lock) for team use. Modules for reusable patterns.
3
CDK: define cloud resources in TypeScript/Python — generates CloudFormation. Better for developers who think in code rather than HCL. Enables type-safe constructs and unit-testable infrastructure.
4
GitOps: infrastructure changes flow through PRs. Automated plan on PR, apply on merge to main. Drift detection alerts when real infra deviates from repo state (Atlantis, Terraform Cloud).
declarative vs imperativestate fileplan / applymodulesGitOpsdrift detection
High
CI/CD pipeline design
1
Pipeline stages: commit → lint + unit test → build image → integration test → security scan (SAST/SCA) → push to registry → deploy to staging → smoke test → deploy to prod (canary) → full rollout.
2
Shift-left: move security and quality checks earlier. SAST in pre-commit hooks, dependency scanning in CI, container image scanning before push. Cheaper to catch vulnerabilities before they reach staging.
3
Rollback strategy: immutable artifacts — never patch in place, always redeploy previous image tag. Database migrations need backward-compatible schema changes (add column before removing old one, two-phase migrations).

Medium
Container image security & supply chain
1
Minimal base images: distroless or Alpine — fewer packages = smaller attack surface. Multi-stage builds — compile in a fat image, copy binary into a minimal runtime image.
2
Image signing (Cosign/Sigstore): sign images at build time, verify signature at admission (Kubernetes OPA/Gatekeeper). Prevents running unsigned or tampered images in production.
3
SBOM (Software Bill of Materials): list of all dependencies in an image. Required for vulnerability tracking and compliance. Generated by Syft, embedded in image attestation.

What FAANG tests: At senior+ level, interviewers explicitly ask "what would this cost at scale?" and "how would you optimise it?" Cost awareness is a signal of production experience.
Compute cost levers
Spot, reserved, on-demand
On-demand: full price, no commitment. Reserved: 30–60% discount, 1–3 year commit. Spot/preemptible: 70–90% discount, can be reclaimed in 2 min. Design for spot: stateless workers, checkpointing, graceful shutdown on SIGTERM. Use spot for batch jobs, ML training, CI workers — never for stateful or latency-sensitive workloads.
Data transfer costs
Egress is expensive, ingress is free
Cross-AZ data transfer costs ~$0.01/GB — significant at scale. Cross-region is higher. CDN offload reduces egress from origin. Co-locate services that talk frequently in the same AZ. VPC endpoints for S3/DynamoDB eliminate NAT gateway egress costs. At 1PB/month egress, $90k/month in AWS data transfer charges.
Right-sizing
Match instance to workload
CPU-optimised (C family) for compute-intensive. Memory-optimised (R/X family) for in-memory DBs, caches. Storage-optimised (I/D family) for high IOPS. GPU (P/G family) for ML inference. Oversizing is common — use CPU/memory utilisation data over 2 weeks, target 60–70% average utilisation for headroom.
FinOps practices
Cost allocation & optimisation
Tag every resource with team, service, environment. Budget alerts at 80% + 100% of monthly target. Savings Plans for predictable base load (more flexible than reserved). S3 Intelligent Tiering for mixed-access data. Delete unused snapshots, unattached EBS volumes, idle load balancers — these silently accumulate.
Key trade-off table
What you give up for each gain
Multi-region HA → 2–3× cost + replication complexity. Synchronous replication → high write latency. Active-active → conflict resolution complexity. Serverless → cold start + vendor lock-in. Spot instances → interruption risk. CDN caching → stale content window. More AZs → cross-AZ transfer cost.
Interview signal
How to demonstrate cost awareness
After proposing a design, volunteer: "At 10M DAU this generates roughly X GB/day of egress — that's about $Y/month. I'd use CloudFront to cache static assets and reduce origin egress by ~80%." You don't need exact figures — order-of-magnitude estimates with clear reasoning are the signal.
