All four conditions must hold simultaneously. Break any one and deadlock is impossible.

Condition 1
Mutual exclusion
At least one resource is held in a non-shareable mode — only one thread can use it at a time.

Break it: make resources shareable (e.g. read locks, immutable data).
Condition 2
Hold and wait
A thread holding at least one resource is waiting to acquire more.

Break it: acquire all resources atomically at once, or release before requesting new ones.
Condition 3
No preemption
Resources can't be forcibly taken — a thread releases them voluntarily.

Break it: allow preemption — if a thread can't acquire all resources, it releases what it holds and retries.
Condition 4
Circular wait
A circular chain: T1 waits for T2's resource, T2 waits for T3's, …, Tn waits for T1's.

Break it: impose a global lock ordering — every thread acquires locks in the same numeric order.
Memory hook: Mutual exclusion · Hold and wait · No preemption · Circular wait → MHNC or "Men Hold No Circles"

A resource allocation graph (RAG) makes deadlock visible. Threads are circles, resources are squares. An edge from resource → thread means "allocated". An edge from thread → resource means "waiting".

Detection rule: if the RAG has a cycle and each resource has only one instance → deadlock is guaranteed. With multiple instances per resource, a cycle is necessary but not sufficient — run the Banker's Algorithm to confirm.
Prevention
Eliminate a Coffman condition
1
Lock ordering — assign a global numeric ID to each lock; always acquire in ascending order. Breaks circular wait.
2
Acquire all-or-nothing — try to claim all needed resources atomically; if any fails, release all and retry. Breaks hold-and-wait.
3
Timeouts — tryLock(timeout) releases held locks if blocked too long. Adds preemption.
Avoidance
Stay in safe states
1
Banker's Algorithm — before granting a request, simulate allocation and check if a safe sequence exists. Only grant if safe.
2
Cost: requires knowing max resource needs in advance. High runtime overhead — rarely used in production OS kernels, but conceptually important for interviews.
Detection + recovery
Let it happen, then fix it
1
Periodically scan the RAG for cycles using DFS.
2
Recovery options: kill one thread in the cycle (victim selection), preempt a resource, or rollback a transaction.
3
Used by: database engines (PostgreSQL detects deadlock cycles in lock wait graphs and kills one transaction).
In practice at FAANG scale: lock ordering + tryLock timeouts are the dominant production pattern. Banker's Algorithm is an interview concept. Deadlock detection is left to the database layer.
Problematic
Classic AB / BA deadlock
// Thread 1
lock(A); lock(B);   // A → B

// Thread 2
lock(B); lock(A);   // B → A
// T1 holds A, waits B
// T2 holds B, waits A → deadlock
Fix: lock ordering
Consistent global order
// Both threads always acquire
// in the same order: A before B
void transfer(Acct a, Acct b) {
  Acct first  = min(a.id, b.id);
  Acct second = max(a.id, b.id);
  lock(first);
  lock(second);
  // do work
  unlock(second);
  unlock(first);
}
Fix: tryLock + backoff
Release on timeout
while (true) {
  if (a.tryLock(100ms)) {
    if (b.tryLock(100ms)) {
      // success
      break;
    }
    a.unlock(); // release, retry
  }
  sleep(random backoff);
}
Fix: single lock / actor
Eliminate shared mutable state
// Serialize all mutations through
// one coordinator — channel or
// actor — no two-lock acquire

Q: "How do you prevent deadlock in production?" ↗
Lock ordering is the first tool — assign a total order to all locks and always acquire in that order. This eliminates circular wait (condition 4). In a bank transfer: sort accounts by ID, always lock lower ID first. For tryLock: set a timeout; if you can't acquire within N ms, release everything and retry with jitter — this adds de-facto preemption. At the architecture level: prefer a single coordinator (actor, channel, or serialized queue) to eliminate multi-lock scenarios entirely.
Q: "How does a database handle deadlock?" ↗
PostgreSQL maintains a lock wait graph. Periodically (deadlock_timeout, default 1s) it runs a DFS over the wait graph to find cycles. When a cycle is found it kills the transaction with the least work done (victim selection), returns an error to the client, and the client retries. MySQL InnoDB does the same but uses a wait-for graph and kills the transaction holding the fewest row locks.
Q: "Deadlock vs livelock vs starvation?" ↗
Deadlock: threads are blocked forever, no progress. Livelock: threads are active but keep reacting to each other with no net progress (two people in a corridor both stepping the same way). Starvation: a thread is perpetually denied resources — not blocked, but never scheduled. Fix livelock with randomised backoff. Fix starvation with fair scheduling (priority aging, FIFO queues).
Q: "Explain Banker's Algorithm" ↗
Dijkstra's Banker's Algorithm checks if a state is safe before granting a resource request. It simulates: can we find a sequence where each thread's max needs can eventually be satisfied with remaining resources? If yes — safe state, grant the request. If no — defer until safe. Limitation: requires declaring max needs upfront (impractical for most real software) and O(n²) per request check. Studied for OS theory; rarely implemented directly in production.
